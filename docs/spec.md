## 1. コンセプト(核)

*セクション更新: 2026-08-13*

### 目的と操作フロー **【決定】2026-08-13**

*※ここがぶれると実装が別物になる。迷ったらここに戻る*

**目的:** ユーザーが「変わる」と決めた行動を30日で身につけさせ、**アプリを不要にすること。**

**手段:** 決意したときの自分の言葉を、サボっているときの自分に届ける。

**ユーザーが登録するのは「毎日同じ時刻にやること」= ルーティン。**


| 項目     | このアプリ              | ToDoアプリ     |
| ------ | ------------------ | ----------- |
| 登録するもの | 毎日繰り返す行動           | 単発のタスク      |
| 完了したら  | 今日の分が済む。**明日また出る** | リストから消える    |
| 期限     | 毎日の時刻              | 締切日         |
| ゴール    | **使わなくなること**       | タスクを捌き続けること |


**⚠ このアプリでないもの(実装しないことの根拠):**

- **ToDo/タスク管理ではない** → 単発タスクの登録機能を作らない
- **記録・分析ツールではない** → 統計・グラフ・達成率の可視化を作らない
- **コーチングアプリではない** → アプリ側が助言・提案・励ましを生成しない

**1日の操作フロー(定常時):**

1. 時刻が来て未完了 → **自分が書いた言葉が通知で届く**
2. 通知をタップ → Today画面の該当項目へ
3. タップしてチェック → その項目の通知は以降キャンセル

**⚠ ユーザーが能動的にアプリを開く必要がない設計にすること。** 通知が入口で、チェックが出口。滞在時間を伸ばす方向の設計は思想に反する。

### アプリ名 **【決定】2026-08-13**

**KATSU**(表示名。バンドルIDは `com.kisshi.gradhabit` のまま変更不可)

**語義の定義 ── ここを取り違えないこと:** 「喝」は禅で**眠っている者を叩き起こす一喝**。罰でも、罵倒でも、精神論でもない。 **厳しいが、敵ではない。**この一行がトーンの基準になる。

- 英語コピー **【決定】**: `A voice from the you who believed.` ※`gentle wake-up call` `Your inner cheer` は**却下**(§9-7)。「喝」から力が抜けるため
- **⚠ 英語圏で** `katsu` **はトンカツ。** App Store検索で料理アプリと混同されるリスクがある。 → **サブタイトルで1行目に打ち消す。** 例: `KATSU — Habits that end` 改名はしない **【決定】**。ただしストア説明文の冒頭で誤認を潰すこと
- `Katsulet` は不採用(cutlet連想を強めるため)

**⚠ App Store の名前は `KATSU` 単独では登録できない 【決定】2026-09-08:** ASC で既に使われていた。App Store の表示名は一意である必要がある。

- **改名はしない。**§1 が「サブタイトルで打ち消す」例として挙げていた `KATSU — Habits that end` を**そのまま名前側に上げる。** これで**名前の重複回避とトンカツ避けが同時に片づく**
- 日本語ロケールは `KATSU 終わるための習慣`。**名前の一意性は言語ごとに要る**
- **ホーム画面のアプリ名(`CFBundleDisplayName`)は `KATSU` のまま。** App Store の表示名と一致している必要がない → **ビルドし直さなくてよい**
- 名前が「終わる」を担うようになったので、**サブタイトルは差別化の核(自分の言葉)に振り替える。** 名前とサブタイトルで同じことを言わない
- 審査で Guideline 2.3.8(既存アプリと紛らわしい)を指摘された場合は `KATSU — Habits designed to end` へ寄せる

**⚠ アイコン 【決定】2026-09-07:** 「喝」の一文字を刃物のように尖らせた字。生成りの字 `#FAF0E0` 系 / 紺地 `#0F1B61`。

- **字を選んだのは、英語圏で** `katsu` **がトンカツだから。**漢字が出ていれば料理アプリと並んでも一目で違う。 サブタイトルでの打ち消しと同じ仕事をアイコンにもさせる
- 尖らせたのは**「喝」が一喝であって応援ではない**ため。丸くすると `gentle wake-up call`(§9-7で却下)と同じ方向に落ちる
- 起動画面も同じ字・同じ紺にする。Expo デフォルトのロゴと水色が **build 5 まで残っていた**

### 一言 **【決定】**

**習慣が身についたらユーザーを卒業させる習慣化アプリ。**

### 思想 **【決定】**

既存の習慣化アプリは、ユーザーの成功(習慣が身につく=アプリ不要になる)と 収益(継続課金)が正面から対立している。だから連続記録で縛り、通知で呼び戻し、 離れると罪悪感を出す設計になる。 卒業モデルはこの矛盾を消す。目標を達成したらサブスクを終了させる。 **解約を敗北ではなく成功として扱う。**

副次的な強み:

- 競合が真似すると自社の収益モデルを壊すことになる。大手ほど追随できず、 **弱者だけが取れるポジション**になる
- 飽和カテゴリでも「二番煎じ」にならない。機能ではなく思想が逆だから

### 差別化の核 **【決定】**

**サボったときに表示する煽り文言を、ユーザー自身が書く。** 例:「お前は自分が変わるって決めたんだろ」

**⚠ トーンの再確認 【決定】2026-08-13:** 外部レビュー(Manus)から「煽りではなく穏やかな応援に再定義してはどうか」という 提案があったが、**却下した**(§9-7)。理由:

1. **既にXで公開済みの主張と食い違う。** `attacking what you did is fine. Attacking who you are is not.` これは「厳しさは残す、人格否定だけ切る」という宣言だった
2. 安全性を担保するために**核まで削っている**。ガードレールは厳しさを消すためではない → **厳しさは製品の主張として残す。** 弱めない。

- アプリが言うと、ただのうざい通知になる(既存アプリはすべてアプリ側の定型文)
- **決意したときの自分が、サボっている今の自分に宛てた手紙**になると意味が変わる
- 現金を賭けさせる設計はApple規約上ほぼ不可能(§5)。 賭けるものを「自分の言葉」にすることで規約に一切触れず、実装コストもほぼゼロ

### build-in-publicとの一貫性 **【調査済】**

出典: 別チャット「Shipaton 2026のbuild-in-public賞戦略」(過去チャット検索で確認) Day 3投稿で既に以下を公開済み:

- "An app that makes you put something real behind the promises you make to yourself."
- "The goal of this app is for you to stop needing it."

→ 卒業モデルは**HAMM収益設計の検討から独立に到達した結論**であり、 公開済みの発言と矛盾しない。物語としての一貫性がある。

*セクション更新: 2026-08-12 / 確度: 全体として **【暫定】**(§8-1で最終確定予定)*

### 画面3つ


| 画面          | 内容                       |
| ----------- | ------------------------ |
| 1. ルーティンを組む | 時刻+やること を並べる             |
| 2. 今日       | 今日のリストが時系列で並ぶ。タップでチェックのみ |
| 3. 自分の言葉を書く | サボり時に見せる文言を書く。**課金ポイント** |


### 挙動

- 時刻になってチェックが付いていなければ、その文言が通知で飛ぶ
- 曜日指定は**入れない**(1.0は毎日固定)。理由は§4の通知64件制限とも噛み合うため

### 何を登録するのか **【決定】2026-08-13**

**時刻が決まっていて、毎日繰り返す、5分〜1時間程度の行動。** 例: `06:30 起きる` / `06:45 瞑想` / `07:00 水を飲む` / `19:00 ジム` / `23:00 寝る`

**扱わないもの(1.0で機能しない入力):**


| 例          | 理由                 |
| ---------- | ------------------ |
| 「週3回ジム」    | 曜日指定は1.0スコープ外      |
| 「今日中にレポート」 | 単発タスク。ToDoではない(§1) |
| 「英語を1時間」   | 時刻が決まらず通知が打てない     |


**⚠ 配色 【決定】2026-09-07:** アイコンの紺 `#0F1B61` を `accent` としてアプリ内に通す。 **押せるもの・選ばれたものにだけ使い、装飾で撒かない。**暗い側では紺が沈むため、役割を反転させて生なりを accent に置く。

- 背景を純白 `#ffffff` / 純黒 `#000000` にしない。**「まだ設定していない」ように見える**
- 未完了は**空の丸**で出す。× も赤も「未達成」の語も使わない。押していないだけの状態を失敗として見せない
- 記号は SF Symbol を使う。`[x]` / `[ ]` のような文字で組むと等幅フォントが混ざって仮組みに見える
- 日付は保存キー(`2026-09-07`)をそのまま出さない

**⚠ 同じ対象の言葉が複数あるときは日替わりで回す 【決定】2026-09-08:** `find` で先頭だけを使っていたため、**`対象: すべてのルーティン` の言葉を3つ書いても2つ目以降が 一度も届かなかった。**保存されているのに永久に選ばれない、書いた本人には不可解な状態。

- そのルーティン専用があればその中から、無ければ共通の中から、**その日ごとに1つ選ぶ**
- **`Math.random` を使わないこと。**予約は画面を開くたびに全消し→貼り直しするため、 毎回引き直すと同じ日の通知がアプリを開くたびに別の言葉に化ける。 **日付とルーティンIDから決まる値**を使い、同じ日・同じ項目なら必ず同じ結果にする
- **日替わりであることを画面に書く。**黙っていると「1つしか届かない不具合」に見える
- 副産物として、**同じ言葉を毎日聞いて慣れる**問題にも効く

**⚠ 課金されたかどうかを、アプリが断定しないこと 【決定】2026-09-08(実機で発覚):** 購入後にペイウォールが `購入は完了しませんでした。請求は発生していません。` と表示したが、 **Apple 側の購入は成立していた。**`purchasePackage` は例外を投げておらず、 その後の entitlement 判定が false だっただけ(RevenueCat の Entitlement に商品が未紐づけ)。

- **「請求は発生していません」と書いてはいけない。**課金された人に嘘をつくことになる。 本番で出れば返金請求とサポート対応を招く
- 購入の結果は4つに分ける: **成立 / やめた / 課金は通ったが解放できない / 購入自体が不成立。** 3つ目を「失敗」に混ぜないこと。**金が動いているかどうかが違う**
- 例外経路でも課金の有無は確定できない。**断定せず「復元を試してください」と案内する**ほうが 誠実で、実際に解決する
- ⚠ **Offering と Entitlement は別の設定。**Offering は「何を売るか」、Entitlement は「買ったら何が開くか」。 前者だけ設定して後者が空、という抜けは起きる。**購入は通るのに機能が開かない**症状になる

**⚠ ペイウォールに価格が出ないときの疑う順 【調査済】2026-09-08:** 実機で `ストアに届きませんでした` が出た件の切り分け結果。

- **RevenueCat の構成は公開キーだけで確認できる。**秘密鍵は不要:
  `curl https://api.revenuecat.com/v1/subscribers/<任意のid>/offerings -H "Authorization: Bearer <appl_の公開キー>" -H "X-Platform: ios"`
  **端末が見るのと同じものが返る。**ダッシュボードを目視するより速く確実
- このとき返ってきたのは `current_offering_id: "default"` と3 Package(tier1/2/3)。 **RevenueCat 側は完全に正しかった**にもかかわらず端末では出なかった
- **理由: RevenueCat は Offering の構成しか返さない。**価格は端末の StoreKit から取る。 商品が降りてこないと Package から落とされ、結果として Offering ごと消える → `current` が `null` になる。 **ダッシュボードが正しくてもこの症状になる**
- **したがって疑う順は App Store Connect が先。** ①有料App契約が有効か ②サブスク3商品が「送信準備完了」以上か(表示名・説明・価格・審査用スクショが揃っているか)
- **Restore が動くことは商品が降りてくることの証拠にならない。** 復元は RevenueCat との通信だけで完結する

**⚠ 日本語対応 【決定】2026-09-08:** 端末の言語が日本語なら日本語、それ以外は英語。**言語切替の画面は作らない**(1.0の画面は3つだけ)。

- **翻訳ではなく書き直し。**「喝」は罰でも罵倒でもなく眠っている者への一喝(§1 語義の定義)。 直訳すると日本語では力が抜けるか、逆に人格否定に寄る。**説明はですます、言い切るところは短く**で書いてある
- **ライブラリを足さない。**文言は101個で、辞書を1つ引けば足りる。`expo-localization` で端末の言語を読むだけ
- **英語版が型の原本。**片方にキーを足し忘れるとコンパイルが通らない
- **`app.json` に `CFBundleLocalizations` を入れること。** アプリ内を訳しただけでは App Store に「日本語対応」と出ない
- **ユーザーが書いた言葉はこの仕組みを一切通さない。**通知の本文はユーザーの文言そのもの
- Tier 1 の判定リストには**日本語が既に入っている**ため、日本語UIにしても安全網に穴は開かない。 ただし一人称と自傷語の近接判定は空白のある言語向けで、日本語は `DIRECT_PHRASES` の部分一致で拾う

**⚠ 自主卒業の出し分け 【決定】2026-09-08(実機確認で発覚):** 入口(`I don't need this anymore`)は**無課金でも常時出す**(§2 自主卒業の決定どおり)。 無料で使い続けた人が離れるのもこのアプリが目指した成功であり、 課金者限定にすると「金を払った人だけが卒業できる」という逆の意味になる。 **ただしモーダル内の解約ボタンは購読者にだけ出す。** 無課金の人を Apple の管理画面へ送っても解約するものが無く、行き止まりになる。

**⚠ 実機で見つけた不具合と作り直し 【決定】2026-09-07(TestFlight build 7):**

- **`Modal` の中には専用の `SafeAreaProvider` を置くこと。** expo-router は root に provider を置くが、 Modal は別のビュー階層なので inset が 0 になり、**オンボーディング先頭の文字がノッチに潜って読めなかった。** `SafeAreaView` を置くだけでは足りない。ペイウォール・卒業モーダル・ルーティンピッカーも同様
- **操作を裸の文字で置かない。** `Save` `Next` `Begin` が `Text` のまま並んでいて、押せるものだと分からず 画面が作りかけに見えていた。**押せるものは必ずボタン部品を通す。**タップ領域は最低 44pt
- **時刻をキーボードで打たせない。** `07:00` を手入力させるのは、毎日決まった時刻を数件登録するだけの操作に対して重すぎる。 コロンの位置も24時間制かも分からない ── **分からせるのではなく選ばせる。** iOS 標準のホイールを使う
- **入力欄のある画面には `KeyboardAvoidingView` を置く。** キーボードが入力欄を隠していた

**⚠ オンボーディングの入力欄に例文を1つ置くこと。** `07:00 — Drink a glass of water` など。 ユーザーは最初の1件で使い方を理解するため、**この例文が実質的なチュートリアル**になる。

**⚠ オンボーディングで必須にするもの 【決定】2026-08-29(実装時):** **ルーティン1件と、言葉1件の両方を必須**にした。飛ばせない。

1. **ルーティン**: 最初の保存日が Day 1(`startedOn`)の起点。ここで立てないと卒業判定の窓が始まらない
2. **言葉**: 文言0件なら通知を1件も送らない仕様のため、飛ばせるようにすると **「何も起きないアプリ」を渡すことになる**。オンボーディングは「決意したとき」の場面そのものであり、 手紙を書かせる場所としても正しい

通知の許可だけは飛ばせる(`Not now`)。許可は端末側でいつでも変えられる上、 拒否されても Today 画面上部に同じ文言を出す導線があるため。

**⚠ 完了フラグは** `AppState.onboardedAt` **に持つ。** `startedOn` で代用しないこと。全ルーティンを削除した人にオンボーディングを やり直させることになる。

### 登録上限 **【決定】2026-08-13: 8件**

- **技術的根拠:** iOSのローカル通知は64件上限(§4)。8件なら余裕を持って収まる
- **体験上の根拠(こちらが本質):** 10件以上並ぶと「その日全部完了」がほぼ不可能になる。 全部完了しないと達成日にカウントされない設計のため、**上限を緩くすると誰も卒業できない**
- 上限到達時の文言例: `Start with a few. You can add more after you graduate.` → **数を制限すること自体がメッセージになる**

### 完了判定 **【決定】2026-08-13**

**その日のうちなら、何時にチェックしても達成扱いにする。**

理由:

1. **時刻厳守を課すと罰のアプリになる。** 7:00の項目を7:05に押して未達成、は UX禁止事項「未完了を失敗として扱わない」と正面から矛盾する
2. **実際にやったかと、押したかは別物。** ジムに行ったが押し忘れた人を未達成にする理由がない。 **このアプリは監視装置ではない**
3. **通知が来てから押すのが正常な導線。** 通知は「時刻を過ぎて未完了」で飛ぶため、 **構造上すべてのチェックが遅刻する。** 遅れを罰すると自分の設計を自分で否定することになる

**実装:**

- `DailyRecord.completedIds` に入れば達成。**チェックした時刻は記録しない**
- 日付境界は**端末のローカル日付**。深夜0時で締める
- **過去日の遡り修正は不可**(1.0)。履歴画面がないため操作導線もない

**⚠ ルーティン削除時の整合 【決定】2026-08-14:** ルーティンを削除したとき、その日の `DailyRecord.completedIds` からも該当IDを落とす。 落とさないと「完了数 > 分母」が発生する。 **過去日は再計算しない**(既に確定した記録は触らない)。

**⚠ 織り込み済みの副作用:** 夜にまとめて全部押せば達成になる。 これは「自分を騙している」だけであり、**このアプリは元々ユーザーを検証しない。** 誰も見ていないから意味がある ── 自分の言葉を書かせる設計と同じ思想。

### 課金 **【決定】2026-08-12**

#### フリーミアムで行く(ハードペイウォールにしない)

- **無料でコア体験が全部成立する。** ルーティン登録・今日のチェック・通知・卒業まで無料
- 無料の制限は**自分の言葉が1つだけ**
- 有料: 言葉の複数登録、項目ごとの出し分け
- ペイウォールは閉じられる。閉じても「今日」の画面に入れる

**この選択は市場データ的には不利(§6: ハードペイウォール10.7% vs フリーミアム2.1%、5倍差)。** 承知の上で選んでいる。理由: **「卒業させる」思想と、入口で金を取る設計が噛み合わないため。** 無料で始め、続いた人だけが課金し、達成したら解約する ── この流れの一貫性を優先する。 転換率の低さは**価格を高めに置くこと**で補う。

#### 価格はユーザーが選ぶ **【決定】**

**同じ内容のサブスクを、価格違いで3つ用意し、ユーザーに選ばせる。** ペイウォールで「このアプリはあなたにとっていくらの価値があるか」を問う形。

- **期間は月額(自動更新)。年額ではない。** **【決定】2026-08-13**
- 価格帯 **【暫定】**: 月 $4.99 / $9.99 / $19.99(§6の相場は月$7.99〜9.99なので中位が標準的)
- 製品ID: `gradhabit.monthly.tier1` / `tier2` / `tier3` **⚠ 製品IDに金額を入れないこと。** IDは変更不可なので、値上げした瞬間に名前が嘘になる
- RevenueCat側は1つのOfferingに3パッケージを入れるだけ

**⚠ 年額を却下した理由(2026-08-13に方針変更。それ以前の「年額$19.99/$39.99/$79.99」は失効):** 30日で卒業させる設計と年額は矛盾する。 年額だとDay 0に1年分を払い、Day 30で卒業しても**残り11ヶ月は返金されない**。 「解約しても金が戻らない」ため卒業が儀式として空虚になり、 むしろ「払った分は使わないと損」という力が働いて**卒業を妨げる**。 月額なら解約で実際に請求が止まる。**思想と課金の時系列が一致する。**

**収益がどこから来るのか(HAMMでの説明の中心):** 30日で卒業する人は1〜2回の課金で終わる。**収益は卒業しない層から来る。** 30日で習慣が身につかない人、途中でサボって仕切り直す人、次の習慣に進む人。 「卒業させても成立する」のはこの構造があるため。

※年額の追加は**9月の論点**。同一グループに足すだけなので後から検証できる。

**⚠ 課金機会は3つだけ 【決定】2026-08-13:**


| #   | タイミング               |
| --- | ------------------- |
| ①   | オンボーディング最後(閉じられる)   |
| ②   | 2つ目の言葉を書こうとしたとき     |
| ③   | 項目ごとに言葉を出し分けようとしたとき |


**それ以外でペイウォールを出さない。しつこく出す設計にしないこと。**

**⚠ 購入画面の必須表示 【決定】2026-09-07(審査要件):** Guideline 3.1.2 は、自動更新サブスクを売る画面**そのもの**に 商品名・期間・価格に加えて**利用規約とプライバシーポリシーへの動くリンク**を求める。 リンクが無いのは定番のリジェクト理由で、実装から**外さないこと**。

- 利用規約は **Apple の標準 EULA** を参照する。自前の規約を書く理由が無く、参照は Apple が認めている方法
- プライバシーポリシーは自分でホストする必要がある。**バックエンドが無いので置き場が無い** ── ページの実体は `docs/privacy/index.html`。 App Store Connect の Privacy Policy URL と同じものを指すこと
- 更新条件の一文も同じ画面に置く(月額・解約するまで継続・Apple ID の設定から解約可能)

**⚠ 課金が切れたとき 【決定】2026-08-13:**

- **書いた言葉を消さない。** 2つ目以降はロック表示にして保持し、再課金で復活する → ユーザーが感情を込めて書いたものを削除するのは、このアプリでは特に許されない
- プラン変更(Apple設定から上位・下位へ)はアプリ側で何もしない。entitlementを読むだけ
- **⚠ ロックは通知側にも効かせる 【決定】2026-09-07:** 画面が「Locked ── still yours」と出しているのに 通知だけがその言葉を鳴らしていた(`notifications.ts` が entitlement を見ていなかった)。 **無料のときは先頭1件を全ルーティン共通で使う。**ロックが表示だけの飾りだと②③が課金機会として成立しない。 ただし**言葉は消さない。使わないだけで、再課金すれば戻る**

**⚠ 課金機会③ の形 【決定】2026-09-07:**

- Your KATSU の各行に `For: All routines ▾` を出し、タップでルーティンを選ばせる。選択肢の先頭は常に **All routines**(出し分けは足すものであって既定ではない)
- **無料の人にも行を見せる。**隠すと存在に気づけず、③が課金機会として成立しない。押した先でペイウォールを出す
- **⚠ ルーティンを削除したとき、その言葉を消さない。全ルーティン共通に戻す。** 消すと「書いた言葉を消さない」と同じ一線を越え、放置すると届く先を失ったまま残る

**技術的な可否 【調査済】:**

- **自由入力は不可。** IAPの価格はApp Store Connectで事前登録した価格ポイントからしか選べない
- **選択式なら可能。** 価格違いの商品を複数用意して選ばせるのは合法で、チップ機能等で広く使われている
- Appleは900近い価格ポイントを持つため、刻みは細かく取れる

**⚠ 実装上の制約:**

1. **「一度決めた額は下げられない」は強制できない。** 同一サブスクリプショングループ内なら、ユーザーはAppleの管理画面からいつでも下位プランに変更できる。 アプリ側では止められない。**「下げられない」を仕様にしないこと。** 演出として見せる場合も、事実と異なる説明はしないこと
2. **商品ごとにApp Store Connectでの登録とSandboxテストが発生する。** **1.0は3つまで。** 増やすと8/14の作業が膨らむ

**HAMMでの語り方:** 実際の支払意思の分布データが取れるため、「戦略の明確さ」を数字で説明できる。 ハイブリッド収益(§6: 全体の10%しかやっていない領域)の一角としても位置づけられる。

### カスタムメッセージの安全設計 **【決定】2026-08-12(司令塔チャットの検討を反映)**

**前提として絶対に外さないこと:** このアプリの核は**「厳しい言葉」であることそのもの**。 ガードレールは厳しさを消すためではなく、**「厳しさ」と「有害さ」を区別するため**に入れる。


| 区分               | 例                            | 扱い          |
| ---------------- | ---------------------------- | ----------- |
| **OK(アプリの核)**    | 「お前は自分が変わるって決めたんだろ」「また逃げるのか」 | **残す。弱めない** |
| **NG(ガードレール対象)** | 存在・人格そのものの否定、自傷や希死念慮に触れる表現   | 検出する        |


判定の基準は一行で言える。**"行動"を責めるのはOK、"存在"を否定するのはNG。**

#### Tier 1: ハードストップ **【1.0必須・決定】**

自傷・希死念慮に類する表現が入力された場合:

- **静的なキーワード/フレーズ判定で検出**(AI判定不要、サーバー不要)
- **誤検知は許容し、見逃しを避ける方向に倒す**
- 該当した場合、**その文言を通知用として保存させない**
- 代わりに「これは通知の文言としてではなく、直接誰かに話した方がいいことかもしれません」 と添え、ヘルプライン情報を表示する

**実装上の注意:**

- **判定リストは本ファイルに列挙しない。** 実装側の設定ファイルとして分離して持つ (仕様書は共有ナレッジであり、この種のリストを本文に置くべきではない)

**⚠ ヘルプライン提示の設計 【決定】2026-08-13:**

1. **「危機を検知している」と誤認させない。** 静的判定であり見逃しは大量にある。 見守り・監視を示唆する表現は事実に反し、審査上も医療的主張と見なされうる。 伝えるのは「この文言は通知として保存できない」という事実と、相談先のみ
2. **責めない・驚かせない・説教しない。** ここだけはアプリの通常トーン(喝)から外す。 短く静かに。長文の心配メッセージは書いた本人を追い詰める
3. **ブロックするのは保存だけ。** アプリの利用は止めない。モーダルで閉じ込めない
4. **判定は「自分自身に向けた表現」に限定する。** `kill it at the gym` のような慣用表現まで潰すと実用に耐えない。 一人称+自傷語の組み合わせを見る設計にする
5. **国別の番号表をアプリに持たない。** 更新できず古い番号を出し続けるリスクがある。 **提示先は** `https://findahelpline.com` **一本に確定 【決定】2026-08-23**
  - 「緊急時は現地の緊急通報番号へ」の一文を添える
6. **検知した事実を記録・送信しない。** ログにも分析にも残さない(§4の方針と同じ)
7. **一度の入力につき一度だけ表示する。** 繰り返すと威圧になる

#### Tier 2: ソフトガード **【9月送り・決定】**

「一生」「絶対」「価値がない」など、行動ではなく人格・存在を断定する言葉を検出したら、 **保存はブロックせず**、やんわり言い換えを提案する。 例:「これは"お前"自身を否定する言葉になっています。"今日のお前"を叱る言葉に変えてみませんか?」

**⚠ 1.0には入れない。理由は技術的制約:** 軽いAI判定(Claude Haiku等)を使う案だったが、 **APIキーをクライアントに埋め込むことはできない**(抽出・悪用される)。 実行にはサーバー側が必要 = §4のバックエンドなし決定と衝突する。 → **9月にIAPステーク(§5-B)でEdge Functionを立てる際、まとめて実装する。** 判定は保存時の1回のみ(通知のたびではない)。

※どうしても1.0に入れたい場合は、静的な語句判定で警告だけ出す簡易版なら サーバー不要で実装可能。**ただし優先度は低い。8/29提出を優先すること。**

#### 時間経過での聞き直し **【9月送り・暫定】**

書いた瞬間は良い緊張感でも、同じ言葉を10回・20回読むうちに刺さり方が変わりうる。 一定回数表示された文言について「この文言を◯回見ました。まだこの言葉でいいですか?」 と聞き直す仕組み。安全面にも体験面にもプラスだが、**1.0の必須ではない。**

#### App Store審査への影響 **【暫定】**

1.0は**本人だけが自分の文言を見る設計**(公開ボードなし)のため、 UGCモデレーション要件が本格的にかかる可能性は低い。 ただし**審査時のレビューノートに「自傷的な文言に対するガードレールがある」旨を一文入れる。** 心証にプラスであり、コストはゼロ。

#### 文言の制約 **【決定】2026-08-23**

- **上限60文字**(コードポイント単位。`[...str].length` で数えること。`.length` だと絵文字が2文字扱いになる)
- 根拠: 英語だと日本語の約2倍の文字数を要する。 `You said you were going to change` = 33文字、`Nobody's coming to save you. Get up.` = 36文字。 40では英語が窮屈で、80では二文の説教が書けてしまう。 **「一撃であること」を保ちつつ英語でも成立する幅**が60
- 登録上限8件と同じく、**制限そのものがメッセージになる**

#### 入力テキストの安全な取り扱い **【決定】2026-08-23**

**現構成でインジェクションは成立しない**(確認済み): React Nativeの`<Text>`はHTMLを解釈しない / WebView未使用 / AsyncStorageはSQLではない / **v1.0にLLMが存在しない** / 通知bodyはプレーン文字列

**それでも守ること:**

1. **保存は必ず**`JSON.stringify`**を通す。** 文字列連結でJSONを組み立てない
2. **Tier 1判定の直前に正規化をかける。** ← 実務上もっとも重要 `normalize('NFKC')` + ゼロ幅文字の除去 + 連続空白の圧縮。 ゼロ幅スペースや異体字を挟むだけで静的判定は容易に回避できるため。 **保存する文字列は元のままでよい**(正規化は判定用)
3. **通知のペイロードにユーザー本文を入れない。** タップ後の遷移はルーティンIDだけで解決させる。文字列を経路情報に混ぜない
4. **⚠ 9月のTier 2で前提が変わる。** AI判定を入れるとユーザー文言がLLMに渡るため、 **プロンプトインジェクションが現実の脅威になる。** ユーザーテキストは常にデータとして扱い、指示として解釈させない設計が必須

### 卒業の扱い **【決定】**

- 1.0では「**30日固定**で、続いたら卒業を提案する画面が出る」だけ

**⚠ 判定の定義 【決定】2026-08-13(Manusレビューで未定義が発覚したため確定):**


| 項目      | 定義                                 | 定数名                         |
| ------- | ---------------------------------- | --------------------------- |
| 起点      | **最初のルーティンを保存した日 = Day 1**         | `START_ON_FIRST_ROUTINE`    |
| 判定窓     | **直近30日のローリング**(固定チェックポイントではない)    | `GRADUATION_WINDOW = 30`    |
| 達成条件    | **その30日のうち21日以上で「その日のルーティンを全部完了」** | `GRADUATION_THRESHOLD = 21` |
| 判定タイミング | **毎日**。条件を満たした時点で卒業提案              | —                           |


**⚠ ローリング判定にした理由 【決定】2026-08-13:** 「Day 30で判定」だと、そこで未達だった人に**「失敗した瞬間」が生まれる**。 これはUX禁止事項「未完了を失敗として扱わない」と矛盾する。 ローリングなら、失敗という瞬間がアプリ内に一度も存在しない。 かつ**Day 45で条件を満たした人もその日に卒業できる**。思想としてもこちらが正しい。

**⚠ 連続記録(streak)を条件にしないこと。** 1日落としただけでリセットされる設計は上記と同じ理由で不可。 **2つの定数を1箇所に置く**こと(§3-2の実装要件)。9月に調整する。

**⚠ Day 1の分母の例外 【決定】2026-08-13:** 登録時点で既に時刻が過ぎている項目は、**Day 1に限り分母から外す。** (22時にインストールした人の「7:00 起床」でDay 1が確実に未達成になるのを防ぐ) Day 2以降は「その日終了時点に存在する全ルーティン」が分母。

**⚠ 判定の細部 【決定】2026-08-13(実装時に未定義が発覚したため確定):**


| ケース                      | 扱い                                           | 理由                                                       |
| ------------------------ | -------------------------------------------- | -------------------------------------------------------- |
| **ルーティンが0件のとき**          | **卒業判定そのものを実行しない**                           | ルーティンが無い人は「卒業を提案する相手」ではない。全削除して30日放置した人が卒業できてしまう穴も同時に塞がる |
| **Day 1で時刻超過により分母0**     | **達成扱い**                                     | ルーティンは存在する。インストール時刻で不利にしない                               |
| **アプリを開かなかった日**          | **未達成**。レコードを遡って作らない                         | —                                                        |
| **Day 1の分母外項目をチェックした場合** | **分子にも分母にも入れる**                              | `[x]`が付くのに数字が増えないのは矛盾。遅れてやった人を罰しない(完了判定の思想と一致)           |
| **Day 1中に時刻を編集した場合**     | 除外判定は**初回計算時に確定**し`DailyRecord`に永続化。以後再計算しない | 「過去日は再計算しない」方針と揃える                                       |


**⚠ 補足:** Day 1にルーティンが0件になることは構造上ない (オンボーディングで最低1件の登録が必須で、その保存日がDay 1の起点のため)。 0件が起きるのは**途中で全削除した場合のみ**であり、上記の「判定を実行しない」で足りる。

**⚠ UI上の注意:** Day 1の分母外項目に `Not counted today` のような表示を出さないこと。 内部ロジックをユーザーに説明する必要はなく、「数えられない」は体験として冷たい。

**⚠ 卒業判定の役割を取り違えないこと 【決定】2026-08-13:** これは「習慣が身についたことの証明」ではない。21日に科学的根拠はない。 役割は**「もう要らないんじゃないか」と問いを出すこと**。 人は自分が卒業できる状態にあることに気づかず惰性で使い続けるため、誰かが聞く必要がある。 **決めるのはユーザーで、アプリは問いを出すだけ。** → この理解に立てば、閾値が多少ずれていても構わない。

**自主卒業 【決定】2026-08-13:** `I don't need this anymore` を常時置く。 判定を待たずにユーザーがいつでも卒業できる。押すと同じ卒業モーダルが出る。 実装は既存モーダルを呼ぶだけ(10行程度)。 **思想としてはこちらが本体。**アプリが許可を出すのではなく、ユーザーがいつでも降りられる。

**⚠ 置き場所の変更 【決定】2026-08-29(実装時):** 当初は「設定画面に置く」としていたが、**設定画面を作らず Routines 画面の末尾に置いた。** 理由: 1.0の画面は3つだけ(Routine setup / Today / Your KATSU)と決めてあり、 自主卒業のためだけに4つ目を足すのは制約と噛み合わない。 Routines は「何を自分に課しているか」を管理する面なので、その一覧の最後に 「もう要らない」が来るのは導線として自然でもある。 **9月に設定画面が必要になった時点で移せばよい。**

**⚠ 自分で呼んだ場合は** `graduatedAt` **を記録しない 【決定】2026-08-29(実装時):** 記録すると、自主卒業を一度見た人に判定由来の提案が二度と出なくなる。 自主卒業は「今の自分の判断」であって、判定の結果を先に消費させる理由がない。 `graduatedAt` を書くのは**判定で出したモーダルを閉じたときだけ**。

- **⚠ 用語の訂正(2026-08-12):「自動解約」は技術的に実装できない。** iOSのサブスクは開発者側から解約できない仕様で、RevenueCatにもキャンセルAPIはない。 アプリができるのは**Appleの解約画面へ誘導すること**(`showManageSubscriptions`)まで。 → **1.0は卒業画面から解約画面へ飛ばす導線だけ入れる。実装は数行。** むしろ自動でやるより、ユーザーが自分の手で解約ボタンを押すほうが儀式として強い。 9月に検討するのは「自動解約」ではなく**卒業後に有料機能を自分で無効化するロジック**
- 「30日」に強い根拠がないことは承知の上で確定させた。 **9月のアップデートで日数を調整できる設計にしておくこと**(定数を1箇所に持つ、 判定ロジックを日数パラメータ化する)。この一点だけ実装時に守れば足りる
- **ストア説明文とペイウォールには最初から書く** → "This app is designed for you to quit it."

**⚠ Tier 1の判定リストをEASクラウドビルドへ届ける方法 【決定】2026-08-29(実装時に発覚):** 判定リスト(`src/config/blocklist.ts`)は上記の通りコミットしないが、 **コミットしないと EAS のクラウドビルドはクリーンな git clone からビルドするため、 このファイルを持たずに落ちる。** 実際に最初の本番ビルドで `Unable to resolve module @/config/blocklist` として発覚した。

判定リストの中身を差し替えたら、EAS側の値も更新すること(手順は `src/config/README.md` に記載)。

**決定の根拠:**

- 1.0が扱うデータはルーティン・チェック状態・自分の言葉のみ。**全部その端末の中で完結する**
- 通知はローカル通知でサーバー不要
- 課金状態の検証はRevenueCatがサーバー側でやる。**自前サーバーの出番がない**
- 複数端末同期・ソーシャル・AI提案は1.0で切っている(§2)ため、サーバーを必要とする機能がゼロ
- 認証を入れないので、**サインアップ画面もアカウント削除機能も不要**になり、 審査項目とオンボーディングの離脱要因を同時に減らせる
- Supabaseを入れると、認証・RLS・スキーマ・オフライン同期の設計が発生する。 **8/29提出に対して、得るものがないのに工数だけ増える**

**実装方針:**

- ローカル保存は expo-sqlite または AsyncStorage。データ量が小さいので後者で足りる
- RevenueCatは匿名App User IDで動かす。復元はApple ID経由で成立する

**⚠ 障害時の要件 【決定】2026-08-13(Manusレビューで追加):**

- **Offerings取得に失敗してもコア体験を止めない。** 最後に取得した entitlement 状態をローカルにキャッシュして判定に使い、 ペイウォールだけ「後で再試行」にする。オフラインでも今日のチェックと通知は動くこと
- **保存済み文言の再検査は入力時のみで足りる。** 起動のたびに全件走査する必要はない。判定リストを更新した場合は、次回編集時に効けばよい
- **データが端末内にしか無いことを、オンボーディング最後に1行で伝える。** 例: `Your words stay on this device.` → 欠点を隠すのではなく、**プライバシーの強みとして出す**

**⚠ ペイウォールの操作は必ず結果を返す 【決定】2026-09-07(TestFlight実機確認で発覚):**

- **`Restore` を押しても何も起きなかった。** 実装は動いていて、復元対象が無いときに画面へ何も出していなかっただけ。 **自分で押したボタンが黙っていると、ユーザーには壊れているのと区別がつかない。**
- 復元の結果は3つに分ける: **復元できた / 復元するものが無かった / 店に届かなかった。** 「無かった」と「失敗した」を同じ結果に潰さないこと。原因の切り分けが実機でできなくなる
- **購入は「やめた」と「失敗した」を分ける。** キャンセルは黙って受け入れる(追いかけない)。 ただし本当に失敗したときは一行返す ── Sandbox では購入失敗が日常的に起きるため、 黙るとテストが成立しない
- 通信中はスピナーを出す。ボタンを無効化するだけでは「押せていない」と読まれる

**織り込み済みのトレードオフ:**

- 機種変更・アプリ削除でデータは失われる。**1.0では許容する**(iCloudバックアップに乗る範囲は乗る)
- サブスクの復元自体はApple IDで効くため、課金トラブルにはならない

**⚠ 9月に再検討が必要になる条件(それまでは触らない):**

1. IAPステーク(§5-B)を実装する場合、クレジット残高をサーバー側で持つ必要が出る可能性がある
2. **Tier 2ソフトガード(§2)のAI判定。** APIキーをクライアントに置けないためサーバーが必須 → **この2つは9月にまとめて片付ける。その時点で初めてSupabase Edge Functionを検討する。** **1.0では検討しない。**

**補足: 「ローカル」は「消える」という意味ではない。** AsyncStorage / expo-sqlite のデータは端末に永続化され、アプリ再起動・アップデートでも残る。 iCloudバックアップから復元すればデータも戻る。 実際に失われるのは**アプリを削除した場合**と、**バックアップから復元せず新規セットアップした場合**のみ。 → 唯一の実害は「感情を込めて書いた自分の言葉が、アプリ削除で消える」こと。 **1.0では許容する。**9月にiCloud同期を足すのが素直な解決。

### 通知実装の制約 **【調査済】**

1. **ユーザーが通知をオフにしたら終わり。** 回避策なし → アプリを開いたときにも同じ文言が出る設計が必要
2. **iOSのローカル通知スケジュールは1アプリ64件まで。** 1日8項目×毎日なら足りるが、曜日別・複数目標に広げると溢れる
3. **「未完了なら通知」は素直に実装できない。** ローカル通知は事前予約のため、その時点の完了状態を判定できない。 **先に予約 → 完了したらキャンセル**という逆の実装になる。 設計を誤ると「終わってるのに煽られる」が起きる
4. **通知タップから該当項目へ遷移させる**こと。ないと価値が半減

補足 **【暫定】**: Live Activity / Widget に自分の言葉を出す案もある。 通知より強いがExpoからだと難易度が上がるため9月以降の武器。

## 9. 却下済みの案 ── 再提案しないこと

*セクション更新: 2026-08-12* *⚠ このセクションは別チャットのClaude向けの事故防止用。実際に一度、 別チャットで却下済みの案(医療費請求書・ビザ書類・契約書レビュー)を 本チャットで再提案する事故が起きている。*

### 9-1. 「他人の痛み」系AI **【却下・決定】**


| 案                    | 却下理由                                    |
| -------------------- | --------------------------------------- |
| 医療費請求書・保険EOB解読(米国)   | 自分ごとでない                                 |
| 移民・ビザ書類(IRS/USCIS)解読 | 自分ごとでない                                 |
| 資格試験RAGコーチ           | 自分ごとでない、差別化が弱い                          |
| 契約書レビュー(フリーランス向け)    | 自分ごとでない。**本人が「稼ぐ側にまだ立っていない」ため当事者ですらない** |
| 値付け・交渉支援             | 同上                                      |
| 非ネイティブの案件英語          | 同上                                      |


**共通理由:** 「英語圏で売れそうなテーマ」からの逆算だったため、 毎回「悪くないが自分ごとでない」に着地。2ヶ月毎晩発信するbuild-in-publicでは、 自分ごとでない題材は3週目で発信が痩せる。

**致命的な追加理由(ユーザー本人の指摘・正しい):** これらはすべて**Claudeアプリに書類を貼れば同じ答えが返る=薄いラッパー**だった。

### 9-2. 「今夜の一手」案(エネルギー適応型タスク提案) **【却下・決定】**

残量と使える時間を2タップで答えると、今夜終わるサイズのタスクを1つだけ出す案。 コピー: "Plans around the energy you actually have."

**却下理由:** ユーザー本人が「ぶっちゃけ使わないと思う」と判断。 **疲れて手が動かない夜、人は「何をやるか」を知らないわけではない。** 知っているのに動けない。だから一手を提示されても何も足されない。価値提案が不成立。

※ただしこの案の背景にある洞察(人間のcapacityは毎日一定ではない)は 別チャットで既に公開済みであり、思想としては生きている。

### 9-3. スクリーンタイム / アプリブロッカー系 **【却下・決定】**

## 10. 判断の前提として効いている原則

*セクション更新: 2026-08-12* *※新しい案を検討するとき、このフィルタを通すこと*

### 10-1. 「Claudeに貼れば済むか」フィルタ **【決定】**

汎用チャットに勝てる条件は4つのみ:

1. ユーザーが持っていない情報を持つ
2. 継続的な文脈を蓄積する
3. デバイス固有の入出力(カメラ/位置/HealthKit/通知/バックグラウンド)
4. 面倒な多段作業を自動完遂する

→ **本案は②③で成立している。**

### 10-2. 「Day 0で価値が出ないと失格」は撤回済み **【決定】**

RevenueCatのデータ(3日トライアル解約の55%がDay 0、有料転換の50.6%もDay 0)は **課金タイミングの話であって価値の話ではない。** 母集団も既存アプリ市場に偏っている。 同レポート内にフリーミアム転換の23%が6週間以降という反例もある。

正しい制約: **「初日に何も返せないなら、なぜ2日目に戻るのかを設計で答える必要がある」** → 蓄積型・記録型を一律に除外しないこと。

### 10-3. 「自分ごとでない題材は却下」 **【決定】**

build-in-public本命である以上、2ヶ月毎晩発信できるかが題材の必須条件。

### 10-4. 二番煎じ自体は失格ではない **【決定】**

カテゴリの新しさと成功は別物。必要なのは新規性ではなく**「なぜ自分が作るか」が一行で言えること。** 卒業モデルはこの条件を満たしている(思想が逆なので機能が似ていても別物)。
