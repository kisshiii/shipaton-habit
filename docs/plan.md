## 1. 卒業条件 【決定】2026-10-13

今の「全部やり切った日が66日連続」では、ルーティン3つを各95%こなす人でも卒業確率がほぼ0%。休みを直近7日で2回まで認めると約50%になる(シミュレーション)。

| 項目 | ルール |
|---|---|
| 1日の数え方 | その日のルーティンを全部やり切った日(変更なし) |
| 休み | やり切れなかった日は自動で「休み」。ユーザーの操作は不要。券などの仕組みは作らない |
| 休みの上限 | **直近7日間で2回まで**。連続は途切れない |
| 数え直し | **直近7日間で3回目の休み**が出たら、連続を数え直す |
| 66日の数え方 | **やり切った日だけ**を数える。休みの日は連続を保つだけで、66日には入らない(最短66日、休みを使い切ると最長約92日) |
| ルーティンの追加・削除・名前の変更 | **数え直す**(2026-10-13 改訂)。変更した日が新しい起点(その日やり切れば1日目)。「ルーティンを変えたら、また1日目から」と一言で言える形にする。名前の変更を数え直さないと、名前を書き換えて中身ごと差し替える抜け道になる |
| 時刻の変更 | 数え直さない |
| 卒業後 | 途切れても取り消さない(変更なし) |

**判定の細部**

- アプリを開かなかった日: やり切れなかった日 = 休み
- 今日: 終わるまで休み扱いにしない。やり切った時点で1日に数える
- 数え直した後: 数え直しより前の休みは、直近7日の回数に含めない(含めると数え直した直後にまた数え直しになる)。**3回目の休みそのものも含めない。**翌日から休み0回で始める
- ルーティンが1件も無い日(全部消した日): 休み
- Day 1 の分母の例外: 変更なし。**ルーティンを追加した日も Day 1 と同じ扱い**にし、追加した時点で時刻が過ぎている項目はその日だけ分母から外す(夜に足した朝の項目で、追加した日が必ず休みになるのを防ぐ)。削除・名前の変更の日は外すものが無い
- ルーティンの変更による数え直しの起点は、`DailyRecord` とは別に日付で持つ(過去日を再計算しない方針のため)。**1つではなく全部残す。**卒業日は保存せず記録から毎回出すので、最後の1つだけだと卒業後の変更で卒業日が消える
- 休まず続いている日数(4.): ルーティンの変更で数え直したときも0に戻す。やり切った日数と起点をそろえる
- 既存ユーザー: 今ある `DailyRecord` に新ルールを当てはめて Day 1 から計算し直す(緩くなる方向なので不利になる人はいない)。更新前の変更では数え直さない。**これで卒業に届く人には、次に開いたとき卒業画面を出す。**卒業日は記録上で条件を満たした過去の日

**定数**(`src/constants/graduation.ts`。ロジックに数値を直書きしない)

```ts
export const GRADUATION_STREAK_DAYS = 66;
export const REST_WINDOW_DAYS = 7;
export const MAX_REST_DAYS = 2;
```

**spec.md の §9 に追記する却下案**

- 累計66日(休み無制限): 卒業が「習慣が身についた」の意味でなくなり、途切れないのでやる気の仕組みも成り立たない。期限がなく、課金が何ヶ月も続く人が出るため
- ルーティンごとに66日: 「この3つを66日」と一言で言えなくなるため(開発者判断)
- 66日終わるまでルーティンを変更できなくする: 登録を間違えた人・合わないと分かった人の逃げ道が「やめる」しかなくなり、縛られている感覚が罪悪感をあおらない方針とぶつかるため。変更は自由、変えたら数え直し、とした(2026-10-13)
- ルーティンの追加・名前の変更では数え直さない: できていないものを消す・名前を書き換えて中身を差し替えることで、66日を守れてしまうため(2026-10-13)
- オンボーディングでルーティンを全部決めさせる: 手順が重くなる一方、数え直しで失うのは始めて数日なら1〜2日分で、守るものが小さいため(開発者判断 2026-10-13)
- 休み券を手動で使う: 管理の手間と「使ってしまった」罪悪感が生まれるため
- 週1回の休み: 3件×95%でも卒業確率が約5%にとどまるため
- カレンダーの週で区切る: 週をまたぐと4日連続で休んでも途切れない抜け穴があるため
- 曜日指定: 下の 2. を参照

## 2. 毎日の習慣の案内 【決定】2026-10-13

**曜日指定は入れない。**

- 休みが直近7日で2回まであるので、週5〜6日の行動は曜日指定なしで続けられる
- 週4日以下の行動は「毎日の習慣」の前提から外れる。習慣化の研究(66日)も毎日の行動が前提
- 入れると「予定の無い日」のルールが増え、`Day 23 / 66` の意味が分かりにくくなる
- 利用者から要望が何度も来たら、そのとき考え直す

**代わりに、ルーティン登録の画面(オンボーディングと Routines)に一言添える。**

- 英語: `Pick things you'll do every day. If it's a few times a week, make it daily — gym becomes "move for 10 minutes."`
- 日本語: 「毎日やることを選んでください。週に数回のことは、毎日の形にすると続きます(例:ジム → 毎日10分体を動かす)」
- 文言は実装時に画面に合わせて短くしてよい。意味は変えない
- **続けて、変更すると数え直すことも同じ場所で伝える**(2026-10-13 追加): `Adding, removing or renaming one later starts the count over.` /「あとから足す・消す・名前を変えると、また1日目から数えます。」。オンボーディングの手順は増やさない

## 3. 卒業の文言 【決定】2026-10-13

休みありにすると「連続」ではなくなるため、卒業まわりの文言を変える。

- 卒業画面・証書: `66 days in a row, all done.` → **`66 days. All done.`** / 日本語「**66日、やり切りました。**」
- 「連続」「in a row」という言葉を、アプリ内の卒業まわりから外す
- ストアの説明文・新機能・プロモーションテキストは、1.0.2 の提出前に `docs/asc-listing.md` で直す(研究の言い方を弱める差し替え案も、このとき合わせて書き直す)

## 4. 進捗の見える化 【決定】2026-10-13

Duolingo を参考に、アプリを開いたときに続けたくなる形にする。**借りるのは「数字が見える」「節目を祝う」「休んでも途切れない」の3つ。サボったことを責める通知や演出は借りない。**

| 表示 | 中身 |
|---|---|
| **Today の上部** | `Day 23 / 66` と、66日までの進捗バー。数字はやり切った日の数。その日やり切った時点で数字が増える |
| **休みの残り** | `直近7日の休み 1/2` を小さく。2回使っても赤くしない、警告しない |
| **休まず続いている日数** | 休みを使わずに続いている日数を、連続とは別に小さく出す。休まないことを誇れる、ご褒美側の数字(休むと0に戻るだけで、卒業には影響しない) |
| **節目のお祝い** | 7日・33日(折り返し)・50日に、卒業画面と同じ紺の全面表示を1回だけ。紙吹雪や音は使わない |
| **数え直しのとき** | 「失敗」「リセット」と言わない。次に開いたとき1回だけ「また1日目から。休みは直近7日で2回まで使えます。」を静かに出す |
| **通知** | 変更しない(未完了のときに自分の言葉が届くだけ)。連続が途切れそうという通知は送らない |

**表示の細部**(2026-10-13 追加)

- 数え直した直後は `Day 0 / 66`、バーは空。やり切った日に Day 1 になる
- 卒業後は `66 / 66` で止める。休みの残りと休まず続いている日数は出さない。長く使うほど増える数字を作らない(spec §9-10 の証書と同じ理由)
- `Day 23 / 66` は日付の見出しより目立たせない
- 節目のお祝いは**それぞれ一生に1回。**数え直して同じ日数に届いても出さない。更新した時点で越えている節目は出さない
- ルーティンの追加・削除・名前の変更は、確認ダイアログで先に「また1日目から数えます」と伝える。この場合は、次に開いたときの数え直しのお知らせを出さない(本人が分かってやったことなので)
- 節目の紺の全面表示は、spec §2 デザイン方針「紺はオンボーディングと卒業だけ」の例外として spec に記録する

- CLAUDE.md の「連続日数のカウンターを画面に出さない」は、この計画で**撤回**する。「未完了を失敗として扱わない」「赤字で煽らない」は残す
- 表示の文言は英語と日本語の両方を用意する(今のアプリと同じ)

## 6. ソフトガード(Tier 2) 【決定】2026-10-13 → **1.0.2 に入れる 【決定】2026-10-14**(開発者判断。調べた結果、端末内で実装できたため)

「ユーザーの言葉を端末外に送らない」「サーバーを持たない」の原則は守る。

- 端末内で動くAI(Apple の Foundation Models フレームワーク)で判定できるかを**まず調べる**。Expo から呼べるか、非対応端末をどう扱うか(非対応端末は今の Tier 1 だけ)
- 端末内で実現できない場合は見送る。外部のAI APIに言葉を送る形にはしない
- 1.0.2 の作業が終わってから調べる

**調べた結果と実装 【暫定】2026-10-13:**

- **Expo から呼べる。**自前の小さな Expo モジュール(Swift、`app/modules/katsu-soft-guard`)で `SystemLanguageModel` を呼ぶ。外部のライブラリは入れない
- **非対応端末:** Apple Intelligence に対応した端末(iPhone 15 Pro 以降)で、オンになっていて、モデルの準備ができていて、言語が対応しているときだけ判定する。それ以外は何もしない(今の Tier 1 だけ)
- **端末内で完結する:** `SystemLanguageModel` は端末内。Private Cloud Compute は使わない
- **残っている確認:** 実機での判定の精度(厳しいが行動を責める言葉を誤って止めないか、日本語でも効くか)。開発機ではモデルを動かせないため、対応端末の TestFlight で確かめる
- 仕様は spec §2「Tier 2: ソフトガード」
